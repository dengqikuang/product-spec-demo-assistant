# 需求澄清提问

只在常规/复杂流程中读取本文件。以决策树组织澄清：每轮一次询问当前所有可回答、且会改变本次 Spec、Demo 或验收结果的问题（包括影响价值判断、范围或规则的决定）；已有答案不重复问，不用行业惯例补全缺口。

## 交互式提问

- 有 Ask User Question 组件时，优先用它呈现本轮问题前沿，让用户直接点击选项或输入自定义答案；不要把多项决定写成长段文字，再要求用户逐条自由回复。
- 将本轮所有当前可回答的问题放进同一次组件调用；仅将依赖前序答案的问题留到后续轮次。题目保持聚焦、短而具体，并带上必要上下文，避免组件问题脱离需求场景。
- 每个问题给出 2–3 个互斥选项，首项放推荐答案（如果确有推荐），用简短说明解释对范围、规则或 Demo 的影响。组件提供自由填写能力，不额外伪造“其他”选项；如果确实没有合理的封闭选项，可使用开放式组件问题。
- 一题包含多个互相独立的可选项、用户需要组合选择，或答案必须解释复杂条件时，不要把它硬塞进单选题。按决策树拆成当前可独立回答的题目；仍不适合选项化时用编号清单，并说明可直接按编号简答。
- 收到组件答案后，明确哪些决定已确认、哪些仍待补充，再推进下一轮依赖问题；推荐选项不因用户未点击而自动视作确认。最终仍按摘要回放并等待明确确认。
- 如果当前运行环境没有该组件，退回紧凑的编号清单：每题标明推荐项、影响和可直接回复的选项编号。不得因此省略当前前沿中的问题。

先从用户提供的信息、项目文件和可用工具中查明事实，再基于已知事实建立内部决策树，维护未决项、分支依赖和闭环状态。只向用户展示当前可回答的问题前沿，不展示完整内部树；每轮一次问完该前沿全部问题，并说明答案影响。依赖未决答案的问题留到后续轮次，收到回答后更新决策树并推导下一前沿。每题给出推荐答案或选项并说明推荐理由；推荐仅供决策，不视为用户确认。用户已经明确的决定直接沿用。

决策树仅覆盖会改变本次 Spec、Demo 或验收的决定。相关分支已确定或明确标注为不适用即视为闭环，不为穷举细节而扩张问题。闭环标准是开发行为和验收结果明确；纯视觉排版与不影响规则的实现选择由 Agent 在现有规范内处理。常规和复杂需求均适用；快改继续走路由中的轻量流程。

## 问题与价值

- 什么现象触发需求？谁在什么步骤受阻，当前怎样处理，损失或风险是什么？
- 最想推动收入、转化、留存、效率、成本、风控还是体验中的哪项结果？什么现象能判断有效？
- 这是问题、目标，还是已经选定的方案？若不做、维持现状或采用规则/文案/配置等轻方案，分别会怎样？

## 范围与页面

- 本次必须完成的最小闭环是什么，明确不做什么？
- 目标角色、产品表面/系统、真实入口、页面关系和主要状态是什么？不同表面是否必须独立？
- 现有入口、任务、字段、状态和操作哪些必须保留？上下游谁受影响？

## 规则与结果

- 操作前条件、输入和默认状态是什么？操作后先看到什么即时状态，最终结果如何确认？
- 失败、超时、重复提交、取消、无权限和无数据时显示什么，用户下一步是什么？
- 规则按什么对象、状态、时间、范围和优先级判断？

## 业务规则闭环（摘要确认前）

对每个 P0 核心业务对象或任务逐项扫一遍；只把尚未明确、且答案会改变 Spec、Demo 或验收的适用决定纳入树。已有答案不重复，不适用时明确标注 N/A；没有未知项时不输出空表或清单。可将相邻决定合并成场景题，但应保持每题聚焦、答案可判断；每轮同时询问当前前沿所有可回答的问题，不受固定题数限制。

1. **触发与排除**：什么事件、条件或人工入口触发？哪些对象、状态、时间窗或权限明确排除？
2. **时间与统计边界**：从哪个时点开始、到哪个时点结束？迟到、跨日、补录、撤回和重复事件如何计入或排除；有统计时再确认统计对象、去重和刷新口径。
3. **状态生命周期及失效**：有哪些状态、谁或什么动作使其进入/退出？何时完成、取消、超时、过期、失效或恢复，失效后用户还能做什么？
4. **配置生效方式**：使用操作时最新配置，还是创建任务/事件时的配置快照？之后修改影响新建、进行中、已完成还是全部对象，影响从哪个时点开始？
5. **手动与对象变化**：手动触发、重复操作、取消、切换、升级、合并和删除分别怎样处理？是否幂等、覆盖、保留历史或转到新对象？
6. **跨表面对象语义**：B 端、C 端、审核端的名称、对象范围、角色权限是否一致？“当前对象”和“目标对象”在每个页面分别指什么，切换后如何保持同一身份？
7. **任务与记录结果**：何时产生任务或记录，按对象、事件还是批次生成，是否合并或去重？各角色可见哪些字段、状态、时间和后续动作？

### 场景回放提问

摘要前先用用户已确认的内容回放结果，并让用户确认具体页面、任务、记录和状态变化，不只确认抽象规则。决策树的重要分支已闭环后，仍按“摘要确认”整理并等待用户明确确认，不得直接开始正式 Spec 或 Demo：

- **正常场景**：当【对象/前置条件】发生【触发】时，是否按【时间/配置口径】为【当前或目标对象】产生【任务/记录】，并展示【状态与可见字段】？
- **边界/人工场景**：如果【排除条件、手动操作、重复提交、对象切换/升级/删除或配置修改】发生，是否【不触发/只生成一次/保留快照/使任务失效/转移到目标对象】，页面和记录具体显示什么？
- **失败/失效场景（复杂或适用时）**：如果【权限撤销、超时、执行失败或状态失效】发生，任务/记录变成什么状态，用户能否重试、恢复、取消或继续？

至少确认一个正常场景和一个会改变规则的边界/人工场景；复杂需求按适用性增加失败或失效回放。若某项不适用，直接确认“不产生该影响”即可，不为凑格式补问。

## 指标与高风险事项

出现统计、排行、金额、数量或比例时，确认对象、公式、时间范围、纳入排除、去重归属、分组排序、刷新和无数据展示；分开页面展示数据与上线成功度量。

涉及资金、价格/权益、删除、权限、审批、敏感信息、外发或自动执行时，确认入口资格、确认方式、即时状态、最终授权、失败恢复和重复处理，不把“提交”直接写成“完成”。

## 摘要确认

按 `spec-templates.md` 的摘要结构复述已确认内容和剩余缺口，请用户明确确认。列出尚未解决且影响本次结果的缺口，已确认分支不再重复提问；用户须明确确认该摘要后，才输出正式完整 Spec 或开始 Demo。关键规则未确认前只输出摘要和当前问题前沿；沉默不算确认。已确认范围内的快改不重做摘要，一旦关键项变化或出现冲突则回到常规流程。
