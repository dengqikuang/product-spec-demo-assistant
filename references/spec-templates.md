# Spec 文档模板

Spec 是业务范围、规则和结果的唯一基准，面向未参加需求讨论的研发及研发 Agent。仅阅读 Spec 及其明确列出的可访问附件，就应能确定本次全部功能的实现行为和验收结果。只写已确认的产品语言；技术方案由研发结合项目决定，但影响业务结果的数据保留、生效时点、权限与外部依赖行为必须写清。

## 使用方式

- 常规任务使用下面的标准 0～9 结构，简明填完适用内容；不强制补复杂协作、反指标或其他不适用细节。
- 复杂任务只在涉及多个独立表面、高风险动作、复杂权限或指标口径时，在对应 2、5、6、7、8、9 节补充必要细节。
- 快改不重写 0～9，使用文末的“增量说明”结构，并明确未改变的业务基线。
- 第 4 节必须区分现状/存量能力、本次新增、保持不变、明确不做；文末保留 Demo 演示边界。
- 为全部交付功能分配稳定 ID，已有 ID 直接沿用；P0 保留 `P0-01` 等标识，其余可用 `F-01` 等，不为同一功能重复建号。功能清单的首列仅放 ID（P0 必须以 `| P0-01 |` 形式单独占格），优先级与操作另列，以兼容现有 Spec—Demo 映射校验。决定本次结果的规则不得只写“沿用现有”，必须说明现有行为和确认来源。

## 研发可实现的完整性

覆盖本次全部已确认交付功能（包括非 P0），按“功能—终端/角色—页面—字段—状态/场景—操作—结果/恢复”写清业务合同。研发应能从 Spec 确定页面行为、取值与验收结果，不依赖自行体验 Demo 猜业务。业务共性引用统一规则，各终端的详情、列表、表单及导航/返回差异分别说明；具体逐页、逐字段与状态审查合同见 `spec-review.md` 第 3 节。

第 6～8 节共同覆盖全部功能，不能只在功能清单写主成功路径。对实际存在的每种状态写清允许操作与转换；对适用场景给出前置、输入、步骤、预期状态/字段结果和恢复方式。字段样例不能代替来源、计算、枚举、默认、空值和校验等规则。未确认且会改变实现的业务缺口先澄清，不用惯例补成事实。

Demo 演示边界可以排除真实服务接入、落库、生产性能等技术验证，但不能据此省略本次已确认业务流程；阶段性交付排除必须有用户确认。详细规则在 Spec 维护，Demo 与右栏准确引用和实现，三方按业务点一一对应，不要求重复复制整份文档。

### 必须能直接确定的业务细节

下表是适用性盘点，不要求无关功能补规则或穷举无业务差异的组合。相关内容写入标准结构的对应章节，重复使用同一规则位置；不能只放检查清单而没有实际答案。

| 维度 | Spec 必须给出的决定性信息 |
|---|---|
| 业务对象与术语 | 对象含义、唯一识别方式、归属/关联关系及本次使用的数据范围；同名跨端字段、状态与单位保持一致。影响本次结果的存量规则须说明具体行为和来源。 |
| 角色与权限 | 每个适用角色对哪些对象、字段和操作可见、可编辑、可执行；数据范围与操作权限分别说明，区分隐藏/禁用/只读，越权或权限变化的业务结果按适用性写清。 |
| 页面与入口 | 全部页面和适用浮层、入口/前置、对象身份、区域/字段/操作、展示状态、页面间去向及返回后筛选/选择/草稿的保留规则。 |
| 字段与输入 | 每个展示/输入/计算字段的含义、来源、类型/格式、单位/精度、默认/回填、空值、必填/限制、可见/编辑条件、联动顺序、校验时机与错误反馈。不能用样例值代替通用规则。 |
| 枚举与选择 | 固定枚举逐个列全业务值、展示文案、含义及适用条件；动态集合说明业务来源、范围与选择行为，详见下节。 |
| 规则与计算 | 触发条件、输入、完整条件分支和结果；多条件同时满足时的优先级/互斥关系，无条件命中时如何处理。金额/数量/比例写公式、精度、舍入顺序、上下限及适用的零值/负值/空值规则。 |
| 状态与操作 | 全部适用状态及初始/终止状态；每个操作的角色、可用条件、输入/确认、起始状态、触发条件、目标状态、数据变化与副作用。说明失败时哪些变化保留或撤销，不把“提交成功”当成业务最终完成。 |
| 列表与查询 | 数据范围、列取值、排序方向及适用的并列顺序、搜索匹配字段与方式、筛选组合/生效/重置、分页/刷新与操作后列表更新行为。 |
| 时间与配置 | 涉及时间的时区、时间来源、边界是否包含、有效期及跨日等适用规则；配置作用对象、生效时点、新旧记录采用当前值还是快照，后续修改影响哪些对象。 |
| 跨页/跨端与外部依赖 | 同一对象在各角色/终端/上下游的状态和数据如何变化，谁触发、何时可见；异步结果如何变为终态，适用的等待/失败/重试、通知/记录结果。外部依赖未接入时，区分真实产品规则与 Demo 模拟。 |
| 历史与冲突 | 本次变更对已有记录、进行中任务、旧配置的影响；适用的重复提交、多人操作、对象被改动/删除/停用时的处理及用户恢复路径。只写业务结果，不指定锁、事务或迁移脚本。 |
| 验收 | 每个交付功能/关键规则对应可复现的前置数据、输入、步骤和明确预期，覆盖各业务分支、边界及适用异常；预期包含状态、字段值、数据归属/数量与后续去向，不能只写“正常/符合预期”。 |

### 枚举与分支的完整性

- **固定枚举**：状态、类型、角色、操作条件、配置选项等闭合业务集合必须逐值列全；禁止以“等”“例如”或少量示例代替全集。每值说明含义和展示文案，有固定业务编码则沿用并注明来源，不替研发发明接口编码。选择类枚举另写默认/未选、单选/多选、选择约束、排序与“全部”的实际含义；状态枚举关联第 6 节转换规则。
- **动态集合**：人员、组织、商品等不能穷举实例；写清业务来源、候选范围、权限/状态过滤、排序/搜索、默认/回填和空集合行为。已有选中项后来被删除/停用/移出范围时，按适用性说明历史展示、能否继续提交及重新选择规则。
- **组合与兜底**：按会产生不同业务结果的条件建立决策表，覆盖同时满足、全部不满足以及适用的边界。规则冲突的处理优先级必须已确认；未知值/旧值/空值只在实际可能出现时定义行为，不擅自增加业务状态或统一套用“其他”。不要求枚举无意义的笛卡尔积。
- **示例与规则**：示例用于验证通用规则。统计/计算附必要的输入与结果，边界说明包含或不包含；例子、正文和枚举冲突时先定位并确认，不让研发 Agent 自行选一个答案。

### 可开发交付门槛

生成正式 Spec 前及交付前各核对一次：从功能清单逐项追踪到页面/规则/状态/验收，再从字段、枚举、操作和分支反查所属功能；覆盖全部已确认交付范围。以未参加讨论的研发 Agent 视角尝试写出每个分支的条件、处理和预期，凡需要猜业务答案的地方，先查已有确认材料，再澄清并写回 Spec。

- 依赖材料列出准确标题、版本及可访问位置，正文保留实现所必需的规则；不能只写“见聊天记录”“同 Demo”“按现有逻辑”。附件作为 Spec 的明确组成部分，Demo 和旧对话不能承载独有的已确认规则。
- 草稿中的缺口须记录问题、影响功能、待决定内容及开发影响。存在改变实现行为或验收结果的未决项时，不能将对应范围标为“已确认/可开发”；正式完整交付前先闭环。用户明确排除/延期时同步更新范围与依赖，不以备注暗中删除已确认功能。
- 技术实现选择留给研发；如果产品约束涉及处理时效、容量、保留期限或对外行为，写清已确认的可度量要求。未知的业务约束须显式澄清，不能凭惯例补数字，也不为普通需求强制设计接口、数据库或架构。
