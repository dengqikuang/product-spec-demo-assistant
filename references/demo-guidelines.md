# 三栏 Demo 规范

Demo 是已确认 Spec 的单 HTML 交互表达，不是生产系统。从 `assets/demo-template/index.html` 开始，只实现确认的页面、状态和最小数据。

## 参考资料

视觉依据的优先级是：用户本次提供的截图/原型 → 用户确认的对应系统 HTML 外壳 → 当前系统已有页面或 HTML → 三栏母版。低优先级资料不得覆盖高优先级资料。不再维护或读取旧截图基线库。

有参考材料时，先实际查看并做简短映射：

| 来源 | 角色/系统 | 页面与入口 | 状态/viewport | 必须保留 | 允许变化 |
|---|---|---|---|---|---|
| ... | ... | ... | ... | ... | ... |

归属、状态或 viewport 不清楚，或受影响页面缺图时先确认。截图只证明存量页面，不自动产生新增业务规则；敏感值可匿名化，但保持原有长度、数量和信息密度。

把映射压缩进每个页面的 `DEMO_CONFIG.pages[].visual`：

```js
visual: {
  status: "reference", // 无参考时明确写 "none"
  baseline: "用户提供的订单列表截图",
  preserve: ["筛选区单行布局", "表头列序与分页"],
  allowedChanges: ["状态列后新增处理结果", "行内增加重新处理"],
  cases: [{ id: "default", state: "default", description: "默认列表" }]
},
states: [{ id: "default", label: "默认列表" }]
```

`reference` 页面必须有固定 `viewport`、非空 `baseline`、`preserve` 和至少一个 `cases`；无参考页必须写 `status: "none"`，不把想象中的设计当成基线。`states` 至少有 `default`，且列出本次 P0 会出现的成功、失败、取消、空态或弹窗状态。

## 产品表面分流

每页必须声明 `surface`，优先级为用户明确指定的系统/终端，其次是本次截图的实际形态；两者冲突或无法判断时先确认。

| `surface` | 使用规则 |
|---|---|
| `mall-admin` | 复用下方的商城后台统一外壳；一级导航由母版锁定，`adminShell` 只控制当前模块、二级菜单和页签。 |
| `mobile` | 在该页面内使用移动界面，不带入商城导航；按截图填写真实移动 viewport、页面布局和移动操作。明确是小程序时复用 `mini-program` 外壳并保留右上角胶囊；明确是 APP 或 H5 时复用 `mobile` 外壳，必须移除该胶囊。 |
| `custom-admin` | 在该页面内按截图还原该系统自己的导航、页签和内容框架。 |

`mobile` 和 `custom-admin` 是当次 Demo 的页面实现，不是新技能母版。除非用户明确要求更新技能，否则不得把它们沉淀到 `assets/`、`references/`、脚本或 Skill 规则中。

移动页的终端必须在 `pages[].terminal` 明确填写：`mini-program`、`app` 或 `h5`。终端未知时先确认，不假定为小程序。小程序页面保留母版的状态栏与右上角胶囊；APP/H5 不得出现胶囊。产品内容不重画系统状态栏、信号、电量、胶囊或手机设备边框；使用固定 390×844 画布。

一个 Demo 可以同时有商城后台和移动页。仅替换对应 `data-page-panel` 内的实现，页面专属样式使用对应 class/属性限定。母版锁定的商城样式只对商城页生效，即使纯移动 Demo 也无需删除它。

## 页面合同

### 按需业务流程概览

业务流程图按需求复杂度启用，不是每份 Demo 的必选项。先判断读者是否需要理解跨阶段的业务上下文：有三个或更多有意义的业务阶段、多个角色/系统之间交接、线上线下衔接、影响结果的审批/分支/异常恢复，或需要追踪不同阶段的业务留痕时，通常值得画图。单角色、单页面的小调整（如单个字段、按钮、简单筛选），且一句话即可讲清触发与结果时，通常省略。若小功能处于较大业务链路中，只画理解本次方案所需的上下文，不为了“完整”扩成全系统地图。以上是判断线索，不是机械计数门槛；只有图能明显提升对角色、顺序、交接或结果的理解时才添加。

适用时，母版在左栏真实页面之前生成“业务流程概览”，作为中栏默认页；它不是产品页面或 P0，不写入 `pages[]`、`data-page-panel` 或 `data-p0`。不适用时从 `DEMO_CONFIG` 省略 `businessFlow`，母版直接以第一个真实产品页面作为默认页，左栏不出现概览入口，也不留空白图框或占位页。运行时根据可选的 `DEMO_CONFIG.businessFlow` 生成图与右栏图示说明；不要在业务页面插槽里手绘第二份概览。

```js
businessFlow: {
  title: "会员积分兑换",
  summary: "会员选择权益并确认，系统按积分余额完成兑换或给出可恢复提示。",
  outcome: "积分足够时完成兑换；不足时不扣减且可重新选择。",
  boundary: "记录名称与样例数据用于解释业务，不代表已确认的物理数据库表。",
  stages: [{
    id: "confirm",
    label: "确认兑换",
    summary: "核对权益所需积分并处理结果",
    actions: [
      { role: "会员", kind: "trigger", mode: "online", system: "APP · 积分中心", text: "确认兑换所选权益" },
      { role: "积分系统", kind: "execute", mode: "online", system: "积分服务", text: "比较可用积分与所需积分", condition: "按余额分支" }
    ],
    records: [{ name: "兑换记录（业务示意）", sampleData: "权益：精品咖啡券 · 结果：成功" }]
  }],
  readingRules: []
}
```

- 顶行按发生顺序表达方案服务的完整业务流程，每格是一段能被业务人员理解的阶段，不写页面目录或技术模块名。
- 多个独立业务流程按业务顺序从上到下分条展示，每条有名称及完整的“业务流程 / 行为动作 / 系统留痕”三层泳道，不把无先后关系的流程硬连成一条。同一流程中的条件分支仍用动作条件表达，不为了分条而重复整段主流程。各条流程的标题、图框左边缘、行标题列和第一个阶段统一左对齐；行标题固定 164px、阶段列固定 252px，短流程不拉伸或居中以填满最长流程，相同角色跨流程使用相同颜色。
- 行为动作逐项标注 `role`、`kind`（`trigger` 为发起，`execute` 为执行）、`mode` 和动作描述。`online` 必须给出 `system`（系统/终端）；`offline` 必须给出 `location`（现场/线下环节）。同阶段多个角色分别写在对应动作上，不单独放关键角色泳道。需要区分条件分支时用 `condition` 说明。
- 角色标签、线上/线下位置及动作文本允许完整换行，长路径和连续标识也不得撑出所属阶段。卡片和内部网格限制最小宽度，阶段列不随长文案扩张；按内容自动增高，箭头占用动作之间的间距。交付用最长的实际角色/终端路径、多动作和长留痕内容检查卡片越界、文本溢出及相邻阶段重叠。
- 系统留痕写已确认会留下的业务记录/数据及简短示意样例；没有可确认留痕时填 `records: []`。可以使用“兑换记录（业务示意）”一类逻辑名称，但 Spec 未明确物理表结构时，不得声称某数据库表、字段或存储实现已经存在。
- 阶段和留痕只能来自已确认 Spec/需求材料。流程不完整或执行角色、线上系统/线下地点、留痕仍不确定时，先澄清，不虚构“合理默认值”。含假设的演示案例必须显式标成假设并经用户确认。
- `node scripts/scaffold-demo.js <SPEC目录> --check-shell --spec <SPEC.md>` 仅在配置了 `businessFlow` 时校验阶段、动作归属/方式与记录样例，不强制简单需求添加图；`productDemo.audit()` 会按有无流程图检查默认页面及概览导航、中栏、右栏联动。页面状态及实际 P0 仍按普通真实页面校验。

多流程配置保留 `businessFlow` 顶层的 `title`、`summary`、`outcome`、`boundary` 和可选 `readingRules`，以 `flows` 替换 `stages`：

```js
flows: [
  { id: "purchase", title: "购买流程", stages: [/* 已确认的有序阶段，结构同上 */] },
  { id: "refund", title: "退款流程", stages: [/* 退款流程的有序阶段 */] }
]
```

每条流程的 `id` 唯一、`title` 非空，`stages` 至少两项，阶段 ID 在所属流程内唯一；动作与留痕沿用单流程合同。不得同时配置顶层 `stages` 和 `flows`，也不嵌套 `flows`。无论一条还是多条，都使用同一个“业务流程概览”入口及右栏；在右栏解释适用条件和流程间关系。验证至少包含阶段数量不同的两条流程及最长实际文案，检查共同左边缘、列宽与无重叠。

### 固定讲解框架与可编辑内容

外层三栏是给开发讲解需求的工具，不是后台或手机页面的一部分。截图只能决定中栏产品原型，不得影响外层三栏的布局、字号、滚动、显隐和导航行为。

- `DEMO_CONFIG.overview` 写整个需求的目标；`pages[].label` 写页面名称；`pages[].overview` 用一两句话解释该页面新增/调整什么。左栏由运行时生成，不能只给页面目录而没有功能概述。
- 左栏按终端/系统显示分组小标题：流程图归入“方案概览”，移动页面按 `terminal` 分为 APP、H5、小程序；后台按 `pages[].systemName` 分组，未填写时商城页归入“商城后台”、其他后台归入“后台”。多个后台系统必须填写各自的真实 `systemName`。只生成有页面的分组，同组页面保持配置顺序；分组标题不可点击，不是产品页面。
- 中栏每个 `data-page-panel` 是一个独立产品 viewport。母版建立定位包含块和绘制隔离，锁定其尺寸与滚动边界。产品弹窗、遮罩、Toast、悬浮操作和移动底部按钮必须作为所属页面的后代；禁止添加到页面外或使用 `showModal()`、popover、全屏等浏览器顶层机制。移动页在真实设备 viewport 内滚动，底栏需保留内容避让空间。
- `pages[].notes` 解释当前页面的变化、规则、交互结果和边界；状态有不同解释时填写 `states[].notes`（描述/结果/边界覆盖对应字段，规则分组与 Spec 引用追加到页面基础说明）。真实操作完成状态变化后调用 `productDemo.setPageState(pageId, stateId)`，同步右栏；该 API 不会替你实现产品状态。状态恢复、取消、保存也必须同步。不同状态仍属于同一页面，不为弹窗复制整套三栏。
- 中栏只呈现产品真实界面。同页多状态优先通过真实操作进入，必须能返回或恢复；不得把所有状态当作长图堆叠，也不能只声明 `states` 而不实现。外框完整性校验通过不代表交互或视觉通过。

```js
// CONFIG 中的讲解内容
overview: "让组合商品也能作为升级达标条件。",
// pages[] 中
overview: "在已有的关联商品选择中支持普通商品与组合商品混选。",
states: [
  { id: "default", label: "配置页" },
  { id: "picker", label: "选择商品", notes: { description: "选择范围支持两种商品。", result: "确认后回写；取消不提交本次选择。" } }
]
// PRODUCT_SCRIPT 的真实交互中，在渲染选择弹窗之后
productDemo.setPageState("admin", "picker");
```

### 三栏页面联动

“概览”（当前母版标题为“概述”）/ 原型 / 说明必须以同一当前页面状态为唯一来源，保持一一对应。

1. `pages[]` 按真实产品页面拆分入口，如任务列表、新增/编辑任务、任务详情；不能只配置笼统的“任务管理”。新增与编辑使用同一表单页时，以状态区分模式并复用渲染逻辑。
2. 中栏展示当前入口对应的完整产品页面，不用缩略图、静态片段或另一套简化页面。每个业务页面只有一个 panel、一份渲染逻辑和数据来源。
3. 右栏标题由当前 `pages[].label` 生成，不用 `notes.title` 创建另一套页面名称。`notes.description` 写用途与用户目标；`notes.groups` 写主要字段、默认值、展示条件、核心操作、校验及异常；`notes.result` 写状态变化与结果；`notes.boundary` 写 Demo 边界。状态说明可补充或覆盖内容，但仍属于当前页面。
4. 新建、编辑、详情、返回、复制等中栏操作与左栏入口复用同一 panel。产品脚本维护一份共享业务 store（记录、当前记录 ID、表单草稿、模式）；先更新 store 并调用该页面唯一的 render，再调用 `setPageState` 与 `showPage`。禁止中栏自行切换 hidden、手改左栏选中态或右栏文本。
5. 左栏由母版调用 `showPage`，显示相同页面实例，保留已渲染的记录和草稿。无选中记录的详情/编辑入口须显示明确空态或依据已确认规则选择记录，不能暗中伪造不同任务。仅切换导航不应清空草稿；新建初始化、复制生成新草稿、保存回写、取消放弃遵循 Spec。
6. 复制任务可按规则创建新对象，但列表、表单、详情始终读取共享 store。不能为左栏单独复制“看起来相同”的页面、默认值或测试数据。
7. 每个真实入口逐项验证并记录：来源页/动作 → 目标 page ID/状态 → 当前记录或草稿 → 左栏选中项 → 中栏标题/内容 → 右栏说明标题。三个区域须指向同一业务页面；新增/编辑模式和具体记录也要吻合。运行 `audit()` 辅助检查三栏选中和状态；人工操作验证字段、数据和模式，不能仅靠 ID 一致宣布通过。

```js
// PRODUCT_SCRIPT：同一业务 store、同一 renderForm，供真实操作复用。
const store = { records: [], currentId: null, draft: {}, mode: "create" };
const openEdit = (record) => {
  store.currentId = record.id;
  store.mode = "edit";
  store.draft = structuredClone(record); // 草稿隔离，取消不回写原记录
  renderForm(store); // 唯一的表单渲染函数，目标为 getPage("task-form")
  productDemo.setPageState("task-form", "edit"); // CONFIG 中声明该状态
  productDemo.showPage("task-form"); // 同步三栏，不生成第二个表单
};
```

### 管理后台统一外壳

`surface: "mall-admin"` 的壳结构和导航由 `LOCKED:RUNTIME` 自动生成，样式在 `LOCKED:MALL_STYLE`，不在 Agent 的可编辑范围。HTML 只提供页面及其 `data-admin-content` 内容节点；运行时会把内容放入标准后台壳。`pages[].adminShell` 配置当前模块、二级菜单和页签；动态变更配置后可调用 `productDemo.renderMallAdminShell(pageId)` 刷新导航。只在内容节点内新增业务 HTML、样式和交互，不手写 `data-admin-shell`、`.admin-primary` 等壳结构或覆盖壳样式。

```html
<section data-page-panel="admin" data-p0="P0-01">
  <section data-admin-content><div class="level-config">本次业务界面</div></section>
</section>
```

- 商品、客户、订单等只改变 `activeModule`、`secondary`、`tabs`、`localTabs` 及内容区，不改变外壳的 1791×1120 viewport、列宽、颜色、字号、选中态、一级导航清单、图标体系或层级。
- 用户提供新的客户或订单二级菜单、页签时，替换配置数组并保留现有 HTML 结构；没有材料时不得编造另一套菜单体系。
- 用户本次截图若使用不同导航体系，允许只在该需求输出的 `demo/index.html` 内替换 `PRODUCT_STYLE`、`PRODUCT_HTML`、`CONFIG`、`PRODUCT_SCRIPT` 以还原截图；不得借此修改母版、脚本、Skill 或参考资料。只有用户明确提出“更新技能”或“更新模板”时才更新它们。

`adminShell` 最小结构为：`activeModule`、`activeSecondary`、`activeTab`、`activeLocalTab`、`secondary: [{ label, children }]`、`tabs`、`localTabs`；商城后台页的 `viewport` 使用母版基准 `{ width: 1791, height: 1120 }`。不得出现 `adminShell.modules`，不得重画一级导航或缩小画布来“完整露出”。脚手架逐页校验内容入口、导航配置、viewport、状态映射和占位符；运行时 `productDemo.audit()` 补查实际尺寸、导航与说明同步。

- 模板是不可替换的黄金母版。`LOCKED:*` 固定封面、工具栏、三栏、开关、导航生成、右栏结构和公共运行时；概述、中栏原型和说明栏始终是同层网格列，左右栏不得以浮层覆盖中栏。只能编辑四个 `EDITABLE:*` 插槽：

| 插槽 | 只负责 |
|---|---|
| `PRODUCT_STYLE` | 业务页面样式；全部规则写在唯一的 `@scope ([data-page-panel])` 内，并使用业务根 class 限定。不能用全局 button/span/* 规则改到商城壳，不能使用 !important、整体缩放或外部资源 |
| `PRODUCT_HTML` | 中栏存量页面与本次增量，每页一个唯一 `data-page-panel` |
| `CONFIG` | 标题、整体概述、逐页功能概述、页面入口、参考来源、目标 viewport、P0 ID 与页面/状态说明 |
| `PRODUCT_SCRIPT` | 已确认 P0 的产品交互；用 `productDemo.getPage(id)` 查询产品节点。商城壳启动时自动生成，只在导航配置变化时调用 `renderMallAdminShell(pageId)` 刷新 |

- `DEMO_CONFIG.pages` 与 `data-page-panel` 按唯一 `id` 一一对应；公共运行时据此生成左栏、切换页面、同步右栏，并公开 `productDemo.getPage/showPage/setSide/getState`。不得手写第二套导航或三栏运行时。
- 左栏入口、页面标题、中栏内容和右栏说明必须一一对应。只有真实存在两个以上状态时才添加状态 Tab。
- 中栏只出现最终产品文案、数据、控件和状态；需求说明、设计理由、验收、制作提示和 Demo 边界只放右栏或 HTML 注释。模板的 `product-stage` 是固定逻辑画布的滚动承载层；页面以 `viewport` 尺寸 1:1 绘制，不读取三栏可用宽度做响应式重排，也不使用 `transform: scale(...)`、`zoom`、整体压缩字号或缩小后台列宽来塞进当前可视区域。
- 中栏滚动条默认弱化隐藏，内容超出时在鼠标悬停或键盘聚焦对应区域后显示细滚动条。业务区域使用 `overflow: auto`，不强制常驻 `overflow: scroll`，避免无实际溢出或重复嵌套滚动；真实长列表和超宽画布仍须能用鼠标、触控及键盘完整浏览，不用裁切内容来消除滚动条。
- 右栏必须足以让开发独立理解当前页面的功能与规则，按字段和操作分组详细说明；可内嵌对应 Spec 章节，不以摘要或“详见 Spec”代替规则。只引入与当前页相关的内容。
- 公共运行时使用 `data-page-target` / `data-page-panel` 建立页面切换；使用 `productDemo.renderMallAdminShell(pageId)` 输出商城后台锁定一级导航、二级菜单和页签；把相同 P0 ID 同时写入 `pages[].p0` 和对应页面的 `data-p0="P0-xx"`。

## 中栏高保真要求

正式交付的中栏必须是高保真交互原型，目标是让读者看到接近实际使用的产品页面，而不是需要自行想象的线框或示意布局。适用于后台、APP、H5 和小程序；业务流程概览仍是方案说明图，不套用产品界面标准。外壳预览和制作中的骨架可以保留占位，但不得当作正式需求 Demo 交付。

- **完整界面**：在对应终端画布内呈现真实的页面层级、业务区域与操作入口。有参考时遵守现有系统的布局、组件和密度，不为“好看”另换风格；无参考时沿用对应外壳的视觉体系，完成业务内容设计，不能只把文字放入通用卡片。
- **视觉细节**：同类标题、正文、辅助文字、按钮、表单、表格、状态标签和弹窗使用一致的样式与对齐规则；文字对比清晰，字号与点击区适合终端。图标实际显示且风格统一，不出现文字溢出、遮挡、重叠、空白图标或不必要的常驻滚动条。
- **可信内容**：使用能解释已确认场景的匿名样例数据，保持合理的字段长度、数量、格式与信息密度；业务字段不得用“内容1”“待补充”等占位代替。没有确认的内容不编造为事实，不为丰富页面新增业务规则或无关功能。
- **真实状态**：本次 P0 控件可实际操作，选择、输入、禁用、校验、弹窗、提交结果及适用空态/异常态与已确认规则一致；状态变化同时更新数据和右栏。高保真不要求接入真实后端，但不能以静态截图或仅弹成功提示代替业务结果。
- **验收证据**：查看默认页及本次关键交互状态的截图，结合实际操作检查上述要求；有参考时另做同 viewport 对比。外壳校验和 `audit()` 通过不证明高保真达标，截图无法取得时明确标记视觉未验证，不宣称高保真验证通过。

## 制作

1. 脚手架完成后先确定每页的 `surface`、左栏功能概述、中栏真实入口与状态、右栏对应解释，再替换母版的 `data-template-placeholder` 为本次页面骨架。若该页是 `mobile` 或 `custom-admin`，只替换该页的产品实现。
2. 有参考图：先还原存量页面骨架、密度、组件、图标和素材，再核对参考。截图工具暂时不可用时仍完成业务实现，视觉项记为未验证，不把工具失败变成半成品交付的理由。
3. 再在 `visual.allowedChanges` 内加入全部已确认 P0，使入口、输入、规则、状态变化和结果可演示。
4. 同步右栏、页面切换和 `states`，确认没有任何 `data-template-placeholder` 残留后，再做人工与浏览器验证。

新增优先复用同页或同系统组件；不得改成通用后台或通用移动页。现有但不相关的控件可保持静态，本次受影响控件必须可操作。删除、替换或合并存量能力必须先回到 Spec 确认。

PC 页面按参考图在 `viewport.width/height` 保留固定逻辑画布，由中栏滚动承载；`mall-admin` 固定 1791×1120，不随截图缩略图或当前浏览器可视宽度改成小画布。移动页面填写真实移动 viewport（如 390×844）。左右栏开关只能改变可视空间，不得触发产品页面自行换版。产品 CSS 全部放进唯一的 `@scope ([data-page-panel])`；产品脚本不得使用 `document/window/globalThis`，查询产品节点和控制页面/栏位均通过 `productDemo`。完成四个插槽后先执行 `node <skill-dir>/scripts/scaffold-demo.js <SPEC目录> --check-shell`，母版完整性、视觉配置、状态和逐页 P0 映射通过才进入浏览器验证。

## 交互与图标

- 开关应控制完整内容；Tab 应切换内容；保存应更新数据、状态或去向；弹窗取消不得提交，确认后应回写触发页面。
- P0 至少包含一个适用的失败、取消、恢复或空数据表现。只改变按钮样式或弹“成功”不算结果。
- 返回、搜索、筛选、新增、编辑、删除、关闭、展开、上传、下载、更多、提示和状态等动作，沿用参考系统图标；无参考时使用母版的 `data-demo-icon="名称"` 或脚本中的 `productDemo.createIcon("名称")`。可用名称见母版 `DEMO_ICONS`。
- 不用 Emoji、字符伪图标、CDN 或联网字体图标。纯图标按钮使用母版图标或下文允许的专有内联 SVG，均须提供 `aria-label` 和足够点击区域。
- 移动端按真实参考布局，默认采用移动阅读密度；分类轨道与商品列表等已确认双列布局应保留。保持滚动和底部主操作可达，不把桌面表格缩小塞进手机。

## 浏览器验证

优先读取并使用 `ego-browser` skill 验证。若连接或截图故障在一次有限重试后仍失败，记录错误并明确告知用户，然后可使用当前可用的浏览器工具继续相同的验证；遵循所用工具的操作规范。用户接管/权限问题必须尊重，不能通过换工具绕过。功能验证与截图验证分别记录：

1. 为同一需求复用一个 Task Space，以绝对 `file://` 地址打开 `demo/index.html`。
2. 检查有效 viewport、默认页面、封面进入、左右栏、页面/状态切换。
3. 按 P0 ID 真实操作成功路径及适用失败路径，并确认状态、数据或去向发生变化。
4. 所有正式产品页面均在目标 viewport 查看默认页与关键交互状态截图，按“中栏高保真要求”核对界面完整性、可读性、组件一致性、信息密度和内容溢出。有参考图时另依次执行 `visual.cases`，核对 `preserve`、层级、比例、密度、滚动、文本、组件、图标和增量融入情况；每个差异要么修正，要么在交付中明确说明。
5. 专门检查框架边界：在后台/移动页之间切换、开关左右栏、滚动长列表、打开弹窗和触发底部操作。验证原型尺寸不变，移动底栏与遮罩始终在当前页面内，旧页面隐藏后没有按钮残留，右栏与当前状态一致，外层标题与左右栏不被覆盖。必须查看整个三栏的截图，不能只截图产品局部就宣称布局通过。

每次页面切换和关键交互后调用 `productDemo.audit()`，所有 errors 必须处理；它不证明业务正确或视觉一致，仍需真实操作和查看截图。所有可用截图途径均失败时将视觉结论标记为 `blocked`，不得冒充通过。按使用工具要求清理本次验证环境。

移动长列表推荐采用固定页面内的三行布局：页头 / `minmax(0, 1fr)` 滚动列表 / 底栏。只滚动列表，底栏留在页面内；弹窗遮罩绝对定位到页面根。不要仅依赖 `fixed` 按钮：它在有滚动的包含块里可能随内容移走，必须实测滚动到底部的可达性。

## 技能维护回归

修改母版或检查器后执行 `node scripts/test-demo.js`。它在临时目录生成商城、移动、其他后台的混合交互用例，验证正例和错误输入的拒绝；输出的测试 HTML 用于浏览器检查。维护测试是框架回归材料，不是业务模板，不得拿来替代用户页面。存量 Demo 使用旧母版时，先保留原文件，将业务插槽迁移到新脚手架并复验，不能仅删除报错或声称旧产物已自动修复。

## 交付门槛

逐项对照 Spec 的 P0：

| P0 | Demo 页面/入口 | 实际操作 | 状态或数据变化 | 可见结果 | 异常 | 验证 |
|---|---|---|---|---|---|---|
| P0-xx | ... | ... | ... | ... | ... | 通过/未验证 |

缺少核心 P0、只完成存量页、只有静态展示或只弹提示时不得交付。中栏仍是线框、占位骨架或存在影响阅读/操作的视觉缺陷时，不得宣称正式 Demo 完成。分别报告功能完整性、运行验证和视觉验证；视觉 `blocked` 不得写成整体通过。

## 迭代边界与交付证据

用户说“改原型”“调整页面布局”“按截图还原”时，默认只指当前 `data-page-panel` 内的业务根节点。先定位 page ID、状态和 P0，再改对应插槽；只有功能概述或业务规则发生变化时同步 CONFIG。不要把产品导航、产品弹窗或页面头部做进讲解外框。只有用户明确要求调整讲解框架，才讨论框架变更。

- 修改前保存当前 Demo 副本或使用已有版本控制，记录受影响页面；修改后检查外框不变及该页面状态切回后的表现。
- CSS 不设置页面根 `:scope`，不重置 `contain/isolation`；业务元素用内层 class。禁止 HTML 内联 style；弹窗采用页面内 `position: absolute`，不使用 fixed。
- 查询从 `productDemo.getPage(id)` 向下进行；不用 `closest` 向上寻找容器，不操作页面根的替换、删除、搬移或其属性/样式。事件委托可用 `page.querySelectorAll(...).find` 的等价遍历或逐控件绑定。
- 旧 Demo 若与当前母版不匹配，先保留原件，识别版本差异。迁移时从当前母版新建临时文件，只移植四个插槽并验证，再替换交付文件；不能直接覆盖旧 Demo 或修改校验器来通过。
- 交付在 Spec 的 Demo 演示边界中附简短映射：`P0 ID / page ID / 入口与操作 / 状态与结果 / 验证结论`。页面状态以实际操作可达为准；切换页面保留还是重置编辑值必须符合已确认规则。

### 图标落地规则

图标唯一来源为母版 `DEMO_ICONS`；运行时可用 `productDemo.getIconNames()` 查看，不凭记忆编名字。静态与动态 HTML 均使用空的 `<span data-demo-icon="search"></span>`；母版会自动初始化动态插入、内容替换和名称变化，也可立即调用 `hydrateIcons(page)`。不要把文字放进该 span，初始化会替换其内容。

默认采用统一的 24×24 viewBox、currentColor 和圆角描边；普通操作图标显示 16～20px，同一组保持尺寸和线宽一致。图标文字按钮用 flex 对齐，间距 6～8px；纯图标按钮提供明确 aria-label，点击区桌面至少 32px、移动至少 44px。尺寸根据真实系统参考调整，不能为了填空而随意混用字符、Emoji 或其他风格图标。

没有匹配图标时，优先用清晰的文字按钮；确需参考系统专有图形时，在当前产品页面内嵌自包含 SVG，保持同组风格并人工检查，不能修改共享母版来适配单次需求。图标按钮仍需可访问名称。

浏览器验证应在默认页、打开弹窗、搜索/筛选后、切换状态后分别检查：图标是否实际出现、是否变成空白/方框、对齐与点击区是否正常；运行 audit 并截图。静态校验与 audit 是工程防误改措施，不是任意脚本的安全沙箱，也不能证明视觉美观或所有 P0 已实现。

## 右栏说明深度与 Spec 章节引用

右栏是当前页面的开发说明，不是功能宣传或 Spec 目录。以“开发不翻 Spec 能否确定默认行为和边界”为验收标准。篇幅随真实规则增长，不设条数上限；用有含义的小标题和逐项规则保持可读，在既有右栏内滚动，不扩大或重画三栏外框。

### 按页面逐项写清

- **列表页面**：数据纳入/排除范围；默认排序字段、升降序、并列时次级排序（适用时）；分页大小、翻页与刷新规则（适用时）。按中栏实际列序说明每一个字段的业务含义、来源或计算/取值规则、枚举与显示文案、格式/单位、空值及条件展示；不能只列字段名。
- **筛选与搜索**：逐个说明默认状态、完整枚举范围或动态选项的来源与范围、单选/多选、全部与未选择的含义、筛选条件之间的组合关系、搜索匹配范围与方式、应用时机和重置结果。日期筛选写时间口径、边界及默认区间（适用时）。
- **新增/编辑表单**：逐字段说明初始值或回填来源、必填、可选范围、输入限制、依赖联动、可编辑/只读条件、校验时机和错误反馈；说明保存、取消、返回、复制对原记录和草稿的影响。
- **详情与操作**：对象来源、字段取值、状态含义、各操作出现/禁用条件、确认过程、状态变化、最终可见结果、失败与恢复方式。
- **所有页面**：用途与用户目标、权限/展示条件、适用异常与 Demo 边界。仅覆盖实际存在的能力；不为凑说明新增分页、筛选或规则。

示例表达应达到“状态筛选默认全部；选项为全部、待执行、执行中、已完成、失败；全部不限制状态；与任务名称搜索取交集；点击查询生效；重置恢复全部并清空名称”的明确程度。此例仅示范粒度，不是默认业务规则。缺失但影响开发或验收的规则回到澄清，不能凭惯例填入已确认说明。

### 在右栏直接阅读 Spec 内容

短规则放 `pages[].notes.groups`。Spec 已有详细规则时，将相关章节的准确标题和规则内容嵌入 `DEMO_CONFIG.specSections`，页面用 `notes.specRefs` 引用。母版直接在右栏显示章节标题及完整的相关规则，读者无需跳转。单 HTML 不请求外部 Markdown 文件，不只放链接或一句“详见第 6 节”。

```js
// CONFIG 顶层；内容必须从本次已确认 Spec 整理，保留条件、例外和数值。
specSections: {
  "task-list-rules": {
    title: "6.1 任务列表 · 排序与筛选", // 与真实 Spec 标题一致
    items: [
      "默认排序：按创建时间降序；创建时间相同时按任务编号降序。",
      "状态筛选：默认全部；选项为全部、待执行、执行中、已完成、失败。"
    ]
  }
},
// 对应 pages[].notes 中
specRefs: ["task-list-rules"]
```

以上仍为示例，不得直接套用其字段与枚举。同一章节在配置中只维护一份，多页面复用引用；内容是当前 Spec 的随 Demo 交付快照。Spec 改动时同步对应章节内容、页面解释和原型行为。引用标题不能编造，不能将未确认规则标成 Spec 结论。

页面基础规则始终保留，`states[].notes.groups` 和 `specRefs` 追加当前状态的差异说明；相同引用去重。状态差异明确写“编辑状态下……”等适用条件，不无声覆盖整页字段规则。

### 交付核对

逐列、逐筛选器、逐操作对照“中栏实际控件—右栏规则—Spec 已确认内容”：检查字段无遗漏、默认值/枚举/排序一致、状态说明准确、引用标题真实且内容随 Spec 更新。检查长说明能在右栏完整滚动阅读，切换页面后不残留上一页章节。结构校验只验证引用存在与内容非空，规则是否完整正确仍需人工逐项核对。

## 系统外壳的制作与复用

公共三栏仅维护 `assets/demo-template/index.html` 一份源文件，它包含组装标记，不用于直接预览。各系统在 `assets/system-shells/<system-id>/` 维护四个片段：

- `content.html`：中栏页面节点，不含外层三栏。
- `style.html`：带 productStyles 的作用域样式。
- `script.html`：产品交互脚本。
- `config.html`：页面、viewport、参考与说明配置。

商城现有锁定样式、导航清单和生成逻辑另存于该系统目录的 `locked-style.html`、`modules.js`、`runtime.js`，由组装器注入公共运行时，保持现有商城合同；这些兼容代码随单文件产物内嵌，非商城页面不会启用其导航。新增系统通常只需四个片段，不改公共框架或组装器。不同系统使用唯一 page ID、业务样式前缀；避免片段之间命名冲突。

用户提供系统页面并要求沉淀时，制作以上片段并记录来源与终端，只维护实际成品。当前系统为 `mall-admin`（商城后台）和 `middle-platform`（中台 PC、custom-admin）。新系统按真实形态选 surface，不因同为 PC 就复用商城导航。
