# `check` 独立产品审查

在执行 `SKILL.md` 定义的精确命令时读取。目标是以研发可据 Spec 独立理解、实现并验收本次已确认业务为标准，发现业务流程、页面交互、字段、状态和场景的遗漏、歧义及冲突，并核对 Spec、可操作 Demo 与右栏说明的逐项一致性。check 的首轮发现阶段只读；完整报告后，须逐项取得用户对全部不通过/未验证内容处理方案的明确决定，决定闭环前不修改 Spec 或 Demo。全部决定完成后，才实施已确认修改并验证关闭条件。不得自行把未决业务规则写成事实，也不得因用户决定保留现状而把失败或未验证标为通过。本轮自行创建的临时验证截图按 `demo-guidelines.md`“验证截图的生命周期”在结论形成且复核完成后清理；这不授权改动目标材料或删除已有图片。

## 0. 执行入口与证据

入口包括当前产品需求上下文中的独立消息 `check` / `CHECK`，以及显式 `$product-demo check` 或选中技能后发送 `check`；讨论或维护命令本身不触发。完整触发边界以 `SKILL.md` 的优先路由为准。

- 开始时声明按本技能的 check 流程执行；先读本文件，再读取目标实际内容。即使历史上下文里已有摘要，也不能凭摘要宣称审完当前版本。
- 执行下面的独立委派步骤，不以主 Agent 主观浏览、通用 code review 或自动校验器替代。子 Agent 工具存在且可用时必须实际调用；工具不可用/调用失败才允许本地兜底，并在结论中注明原因与非独立性质。
- 报告保留简短执行依据：实际目标路径/用户提供的材料、首轮/复查、审查者 ID 或兜底原因、验证范围。未完成委派或未收到实际审查结果时不得声称独立审查通过。后续无变更的重复 check 可以按第 7 节沿用已核实的通过结论，但须标明沿用的审查记录和当前版本核对依据，不假装重新委派。
- `--check-shell`、`audit()`、`auditUI()` 只覆盖相应工程规则，不等于本流程的产品审查；未实际操作 Demo 时应报告静态覆盖及交互/视觉未验证。

## 1. 锁定输入与范围

- 目标优先取当前会话明确指定的 Spec；其次取正在连续讨论或刚修改的唯一 Spec。多个文件不一定代表多个目标，明确属于该 Spec 的附录是输入的一部分。仍有多个合理目标时只问一次目标选择；无目标时请用户提供 Spec 路径或内容，不扫描无关目录、不猜测最近文件。
- 确定目标后，用第 6 节 C01～C06 目录建立检查记录，先判断适用性并记录计划覆盖的页面、状态及证据来源；不因清单出现某类组件而要求业务新增该组件。
- 读取当前实际内容，记录文件路径、版本/状态及本次审查范围；同时读取必要的最新用户确认、关联规则附件与参考材料。已确认变更未写回 Spec 应标为“文档未同步”，不能当成用户尚未决定。
- 如存在明确关联的 Demo，一并审查；没有关联 Demo 且非本轮交付对象时仅审 Spec，Demo 标为“不适用”。本轮要求交付但缺失的 Demo 标为“未验证”，说明交付影响；不能据此否定 Spec 本身，也不能声称 Demo 已交付通过。目标文件读不到或必要证据缺失时说明受限范围，不虚构审查结果。
- 用户最新明确决定作为业务基线；Spec 是交付文档，Demo 是表达与演示。Demo 行为不能反向证明业务已确认。材料之间冲突先定位来源与时间；无法确定时列为待确认。

## 2. 独立委派

首轮新建一个 fresh 子 Agent（不继承完整对话历史），提供目标文件路径或完整内容、关联 Demo/附件、必要的用户确认原文和本审查规范。不要提供主 Agent 的猜测、预设结论、疑似问题清单或修改方案。子 Agent 同时按第 3～4 节建立全部已确认交付业务的三方对应明细，并按第 6 节提交 C01～C06 六项汇总（范围、方法、结果、证据引用），逐业务点的详细证据统一放入对应与验收明细，问题使用 CHK 编号；主 Agent 可补做验证后合并，但不能把子 Agent 未实际验证的内容直接改为通过。子 Agent 只读，不负责修复、不修改文件、发送外部消息或继续委派。

同一目标、同一审查周期的后续 `check` 优先复用首轮审查子 Agent，通过后续任务提供当前材料、变更范围、已确认的问题清单和用户决定，明确要求“修复验证，不重新全面审查”。独立性来自审查者与修复者分离，不要求每轮更换审查者。

在会话中保留审查交接摘要：审查子 Agent ID、目标路径/版本与范围、已覆盖和未验证项、完整问题清单（编号、等级、证据、关闭条件、状态）、用户后续决定。无需为 check 自动创建额外文件。原 Agent 不可用或跨会话时，将这份摘要交给新的独立子 Agent 接续复查；换 Agent 不意味着重置标准。没有前次记录时先查当前会话可用记录，仍无法恢复则说明无法按原清单复查，执行一次新的基线审查，不编造历史。子 Agent 工具确实不可用或实际调用失败时，说明原因并执行相同的本地流程，标记“非独立本地兜底审查”；不能把未尝试调用、审查排队中或只跑校验器写成工具不可用。

### 首轮清单与复查边界

- **首轮全面审查**：按全部适用标准和已确认范围，尽量一次列全影响开发/验收的澄清项与必改项；不能只列最严重的 1～3 项，把其余已发现问题留到下一轮。清单可完整展示，提问仍按优先级每轮 1～3 个。受限材料和未覆盖范围单独列出，不承诺发现所有可能问题。
- **形成基线**：主 Agent 复核后的清单作为后续验证依据。每个必改项写明什么证据或行为满足后可以关闭；关闭条件依据已确认需求，不提前替用户决定未知规则。用户回答后补齐该项条件，不另立一批同根问题。
- **用户逐项决策（新增必经阶段）**：首轮报告必须先完整呈现 C01～C06、业务对应明细及所有未通过/未验证项，不能先修再报。随后按 CHK 编号一次只询问一个未决项，说明证据、影响、处理方案及推荐理由；优先使用 Ask User Question 类交互组件，当前环境没有该组件时，用简短单题文字询问并允许用户自由回答。收到决定后记录在审查交接摘要，并继续询问下一项；若回答揭示依赖问题，先问该依赖，再回到队列。对已有明确用户决定、只是 Spec/Demo 未同步的发现，也逐项确认拟同步方案。用户明确选择“暂不改/接受限制”可闭环该项，但原检查状态仍为不通过/未验证，报告保留风险及理由。沉默、推荐项或 Agent 推断不算确认。所有适用的不通过/未验证项均有明确处理决定后，才进入修改阶段；建议项不影响此门槛，除非用户要求处理。无未通过/未验证项时直接报告完成，无需发起确认。
- **修改与复查**：取得全量决定后，汇总已确认方案与保留项，再按这些决定修改目标 Spec/Demo。完成后由独立审查者按原 CHK 清单和关闭条件复查，实际重测修改影响；未修改项沿用原状态与证据，不得批量改成通过。修改中遇到新业务歧义时，先询问再继续该项，不以实现惯例补答案。check 流程本身仍只读技能规范；修改的是用户确认要修正的被审查需求材料。
- **后续修复验证**：逐项判断未解决、部分解决、已解决，验证修改直接影响的页面/规则/状态；不重新逐章找改进点，不扩大验收标准。无需为无变更、已通过的范围重复验证。
- **新增问题准入**：只有修复引入的实际错误、首轮遗漏且足以阻塞核心流程/权限/数据结果的重大缺陷，或用户新增/改变需求影响的规则，才可加入本轮必改清单。须注明来源（修复回归/重大遗漏/需求变更）、具体证据、交付影响及为何不属于原清单。主 Agent 复核后决定是否成立；首轮重大遗漏应如实承认。
- **其他后续发现**：可选表达改善、未改变既定行为的细化、无关范围的完善需求进入后续建议，不升级为必改、不阻止本轮通过。不能将已证明会造成错误的缺陷伪装成建议来强行通过；不满足重大遗漏门槛的旧有局部问题明确记录影响和后续处理，不声称全局无缺陷。
- **需求变更**：对变更影响范围补审并更新基线，保留原有编号和已解决状态；只有目标实质变化或用户明确要求重新全面审查，才启动新的全面审查周期。

## 3. 按真实场景审查 Spec

### 研发可实现性与完整业务盘点

完整性以本次已确认交付范围为边界，覆盖其中每个功能及适用终端、角色、页面、字段、状态和场景，包括非 P0；P0 是优先级和追踪标识，不是其余功能可以省略的依据。阶段性排除功能必须有用户确认的范围依据，不能由 Agent 自行缩成演示主路径。现有且不受本次影响的系统能力可按明确来源引用，不要求重做全系统。

首轮先从确认材料与 Spec 全文建立业务明细，不能只从当前 Demo 已做出的页面反推检查范围。缺少明确需求 ID 时可在审查记录中给业务点临时编号，不改写 Spec 或虚构新需求。逐项建立“功能 → 终端/角色 → 页面/入口 → 字段与规则 → 状态/场景 → 操作 → 状态/数据变化 → 用户可见结果 → 异常/恢复”的链路，跨页操作沿同一业务对象与数据连续回放。

- **逐页交互合同**：按实际 PC、APP、H5、小程序分别审查列表、详情、表单和适用浮层。明确从哪里进入、展示哪个对象、各状态显示什么、操作何时出现/隐藏/禁用、操作步骤、确认/取消、生效时机、保存/返回后的去向及数据保留。共用业务规则可引用同一章节，终端特有导航、返回、触控/鼠标交互须有相应说明；不能把一端的实现视为另一端已覆盖。
- **逐字段取值合同**：含义、业务来源/计算、枚举与文案、默认值/回填、格式/单位/精度、空值、展示/编辑条件，以及适用的输入限制、必填、联动、校验时机和错误反馈。数据来源按业务对象描述，不强加接口/数据库设计。关键字段不能只写名称或用一个样例代替通用取值规则。
- **逐状态与场景合同**：对本次存在的状态和适用场景，说明触发/前置、允许操作、状态与数据变化、结果反馈、下一步和恢复路径；状态转换说明起点、动作/条件、终点及副作用。覆盖已确认的空数据、加载、失败、无权限、重复操作、边界值等适用情形，不穷举无关异常或无业务意义的组合。不能只枚举状态名，没有状态下的行为。
- **逐操作验收**：研发和测试可以据此得到明确的前置数据、输入、操作顺序、预期字段/状态/结果与失败恢复。缺失会迫使研发自行决定业务的内容应列明确问题，不由 Agent 凭惯例补成事实。完整产品说明不等于自动具备生产技术设计、真实性能或安全验收结论。

审查尺度同时使用 `spec-templates.md`“必须能直接确定的业务细节”“枚举与分支的完整性”和“可开发交付门槛”，检查其实际业务答案，而非是否填满模板：固定枚举是否逐值完整、动态集合是否有范围/失效规则、条件分支是否覆盖并明确优先级、权限/对象身份/时间与历史行为是否足以确定结果、每个交付功能是否对应可执行验收。对适用维度的遗漏须给出会导致不同业务实现的具体场景，不为无业务差异的组合或技术设计提缺陷。

以未参加讨论的研发 Agent 视角，仅凭 Spec 及其列明可访问附件，为各业务分支推导输入、条件、处理和结果；Demo、聊天历史中独有的必要规则不能算 Spec 已完整。已确认答案遗漏在文档中列“文档未同步”，真正未知的业务答案列“业务规则缺口”；已读材料能证明缺项时判不通过，附件读不到而无法判定时标未验证，不替用户猜答案。对应证据合入同一份业务明细及 C01/C02，不另增检查类别。

先建立全部已确认功能（保留现有 P0 标识）—角色—页面/入口—规则—结果的对应关系，再逐项回放。报告必须呈现第 6 节逐项检查结果；每行用简短的实际覆盖与证据说明，不只抄检查标准，也不能只输出发现而省略已检查、未验证及不适用项。

- **范围与入口**：问题与目标是否对应；真实角色、权限、页面关系、前置条件与最小闭环是否清楚；新增、保持不变和明确不做有无冲突。
- **正常路径**：每项已确认功能（含非 P0）从真实入口经过输入/选择、规则判断和状态变化，能否得到唯一可解释、可观察的结果；是否只写了按钮和界面而没有业务效果。
- **适用边界**：取消/返回、重复提交、失败/重试、无数据/无权限、对象变化及任务失效是否会产生不同理解。按业务适用性选择，不强迫每个页面补全部异常。
- **列表与筛选**：排序字段/方向及适用的并列规则；逐列取值、计算、格式、空值；筛选默认值、完整枚举或动态来源、组合逻辑、生效与重置行为。缺失是否真的影响本次结果或开发判断，而非仅不符合模板。
- **表单与详情**：新建默认值、编辑回填、复制规则、字段联动、可编辑条件、校验和反馈；草稿、原记录、保存及取消之间的关系。
- **时间/状态/配置**：适用的统计对象、去重、时间边界、状态生命周期、配置生效范围与时点；跨页/跨端是否描述同一对象与状态。
- **验收**：关键规则是否能写成明确的输入、操作及预期结果；章节、枚举、例子与正文是否互相矛盾。示例不能替代通用规则。

不得发明业务答案、增加未请求能力，或将接口、数据库、技术架构、代码风格、个人视觉喜好当成产品缺陷。“沿用现有”若相关规则与来源已明确可接受；仅靠这句话且会产生歧义才提问题。

## 4. 有关联 Demo 时审查一致性

### Spec—Demo—右栏三方对应

以第 3 节业务明细逐项建立对应关系：先从 Spec 正向找到中栏入口、可到达状态和右栏规则，再从 Demo 控件、状态、样例字段及右栏陈述反向核对 Spec 或最新确认来源。每个已确认业务点均应有对应；同一规则跨页复用无需机械复制段落，但须能准确定位引用与适用条件。三方对应明细必须随最终报告输出，不能只报告相同 P0 ID 或检查类别覆盖。

| 业务点/功能 ID | 终端/角色、页面与状态/场景 | Spec 规则位置及可开发性结果 | Demo 入口、实际操作与结果 | 右栏位置及状态说明 | 三方对应结果 | 功能验证结果/证据/问题 |
|---|---|---|---|---|---|---|
| 沿用需求/P0 ID 或审查临时编号 | 实际覆盖对象 | 准确字段/操作规则位置及四种结果之一，不只字段名 | 实际路径；缺失/未运行须注明 | 当前页/状态及引用，不只标题 | 四种结果之一 | 四种结果之一及证据；失败关联 CHK-xx |

这是一份统一业务对应与验收明细，承载 C01～C04 的逐业务点证据，不再为各类别重复输出整份明细。Spec 可开发性、三方对应、功能验证分别使用四种结果，不能混算；前两者可依据实际文档与静态内容判断，功能通过独立取决于实际操作。字段多时按页面拆成可读明细或引用准确字段清单，但不得合并掩盖某字段/状态遗漏。无关联 Demo 且本轮仅审 Spec 时仍列功能/页面/字段/状态明细，Demo/右栏列标不适用，不宣称三方验收通过；本轮要求交付 Demo 却未提供时属于适用而未验证，不能降为仅 Spec 通过。

全部本次已确认交付业务流程须从真实入口可演示，含适用分支、详情、列表/表单操作及状态恢复。服务返回、权限或外部事件可通过隔离样例数据准备条件并明确模拟边界；业务操作及其结果仍须真实变化，不能用静态截图、只换展示状态、固定成功提示或流程概览图代替。仅说明“不接真实后端”不能豁免已经确认的业务规则；工具无法验证的路径标未验证，不假装已完整体现。


读取 `demo-guidelines.md` 与终端 UI 指引的相关要求。先核对当前文件与 P0 映射；有 Spec 时可执行 `scaffold-demo.js <SPEC目录> --check-shell --spec <SPEC.md>`，绝不执行覆盖或生成操作。旧版本母版不匹配应记录兼容性限制，不能仅据此判定产品需求错误，也不能在 check 中迁移文件。

重点检查：

- 左栏按真实页面拆分，中栏完整页面与右栏对应；中栏新建、编辑、详情、复制、返回和左栏入口复用相同页面、对象、草稿与状态。
- 全部本次已确认功能（包括非 P0）的入口、操作、状态/数据变化、结果和适用异常与 Spec 一致；不能把已声明状态或配置 ID 当成已实现功能。
- 右栏逐字段、筛选、排序、操作和校验的说明是否足够且与原型/Spec 一致；内嵌 Spec 标题与规则有无过时、遗漏关键条件或自相矛盾。
- 外框是否被产品改动影响，图标是否缺失，参考材料中的必须保留项是否被无依据改变。

能安全本地验证时按浏览器技能操作演示副本（必要时在临时目录建立副本或使用隔离会话），不触发真实服务或持久业务修改。对每个受影响入口检查左栏选中、中栏标题/内容、右栏标题及数据身份。动态行为只有实际操作后才能称为已验证；静态代码证据可报告明确缺陷，但不能代替交互测试。验证按实际受限能力分别判定：浏览器交互不可用且没有可沿用的实际操作证据时，受影响功能标未验证；只有截图失败时，仅将依赖截图的视觉子项标未验证，保留已实际操作通过的功能、DOM 与自动检查结果。可以继续静态审查并报告可证实缺陷，但不能用静态阅读填补未完成的运行/视觉验证；工具受限本身不当作产品缺陷，未验证范围不宣称通过。

## 5. 发现必须可核实、可处理

每个有效发现使用稳定编号 `CHK-01` 等，包含：

- **等级与类型**：等级为阻塞/重要/建议；类型为业务规则缺口、文档未同步、Demo 偏差。
- **定位与证据**：Spec 章节/短摘录，或 Demo page ID、状态、控件与复现路径；冲突须列出双方来源。缺失规则定位到应描述它的章节，并检查附件或用户确认中是否已有答案。
- **具体后果**：给一个触发场景，说明会导致哪两种合理实现、错误结果或验收困难。仅说“不够明确”“建议完善”不算有效发现。
- **关闭条件**：列明要补齐的决定/文档内容，或需要通过的具体操作与预期结果；复查不能无新证据提高该条件。
- **处理路径**：已有明确结论的写明需同步/修正到什么规则；真正缺少业务决定的才提出一个具体问题。可给建议并注明建议，不能伪装成已确认结论。

等级按后果判断：

| 等级 | 判定 |
|---|---|
| 阻塞 | 核心 P0 无法形成闭环，或关键权限、数据、状态/结果存在冲突，使受影响范围无法可靠开发/验收 |
| 重要 | 可以理解主流程，但局部字段、边界、状态或 Demo 表达会造成错误实现/结果，需要在受影响范围交付前解决 |
| 建议 | 不影响既定行为和验收，可选的产品表达改善；没有具体收益则省略 |

证据不足的怀疑放“待验证”，不要伪装为确定缺陷。合并同根问题，保留所有受影响页面；不按问题数量考核审查，不把同一个字段缺口拆成多条凑数。

## 6. 主 Agent 复核与输出

主 Agent 阅读每个发现对应原文/当前材料，删除已回答、无证据、不适用或越出需求范围的发现。独立审查意见不是自动成立的结论。核对全部已确认功能及其字段、状态、场景覆盖，保留 P0 标识，无法审查的部分明确列出。

### 六大检查项

首轮和复查均展示 C01～C06 六项汇总。详细规则沿用第 3～4 节，合并分类不减少全部已确认功能、字段、状态与适用场景的覆盖。复查按第 7 节仅重测问题和修改影响，其他范围注明沿用证据、未验证或不适用。目标不明时先请求目标，不生成已完成报告。

| 编号 | 检查项 | 检查内容与证据归属 |
|---|---|---|
| C01 | 业务范围与流程完整性 | 从确认材料盘点全部功能（含非 P0）、终端、角色、权限、入口、前置、正常/适用异常分支及结果；核对新增、保持不变和明确不做的边界，确认流程闭环。引用业务明细和确认来源。 |
| C02 | Spec 可开发与可验收性 | 逐终端列表、详情、表单及适用浮层：对象身份、逐字段来源/计算、枚举、默认/回填、格式/单位/精度/空值、限制/联动/校验；筛选、排序、分页、操作条件、时间/配置生效、状态转换、保存/取消/返回、异常恢复和可复现验收预期。固定枚举/动态候选、条件组合及优先级、历史影响与可执行验收按第 3 节及模板门槛核对；确认研发 Agent 无需补猜业务。 |
| C03 | Spec—Demo—右栏一致性 | 逐业务点双向核对功能、页面、字段、状态/场景、条件、数值、操作及结果，含内嵌 Spec 规则；无遗漏、冲突、过期说明或擅自增加的能力。三方位置和对应结果写入统一业务明细。 |
| C04 | Demo 实际操作与业务结果 | 从真实入口操作全部交付功能（含非 P0）及适用异常，验证状态/数据/去向和对象连续性，以及切页、保存、取消、返回、关闭、改选、失败/重试、重复操作后的保留与恢复；不以静态展示、状态切换或固定成功提示代替业务结果。 |
| C05 | 终端交互与界面质量 | PC、APP、H5、小程序的组件、导航与返回适配；边距/区块/标签/表格/图文/操作区对齐，字号/颜色/密度/阅读顺序/按钮层级/长文案/错误反馈，图标语义与渲染；滚动/溢出/底栏/安全区；名称/标签、触控尺寸、键盘顺序、Escape/焦点恢复；Ego Lite 截图复核默认页及关键状态和参考必须保留项。 |
| C06 | Demo 框架与运行可靠性 | 封面/默认页/导航、右栏默认隐藏及开关、三栏同页同对象同状态联动、四插槽及母版保护、浮层等元素限于所属页面。实际执行 `--check-shell`（有 Spec 附 `--spec`），在覆盖页面/状态调用 `productDemo.audit()` 与 `productDemo.auditUI()`，记录各自结果和兼容性限制。 |

目录不是新增需求清单。无参考图时 C05 仍检查实际截图，仅参考对比子项不适用；图标按任务与系统风格判断，不按数量判错。目标/版本确认、独立委派和主 Agent 证据复核属于执行流程，在报告开头记录，不占检查项。工具是取证方式：同一审计结果可支持 C05/C06，引用一次证据即可，不重复计算通过次数，不能替代业务或视觉验收。

### 结果状态与证据

| 结果 | 判定 |
|---|---|
| 通过 | 该范围已实际检查，满足已确认要求，有当前或核实可沿用的证据 |
| 不通过 | 有证据证明不满足适用要求；关联 CHK 编号及关闭条件 |
| 未验证 | 适用但缺材料、工具受限、未操作、未截图或无可沿用证据；说明原因及缺少的验证 |
| 不适用 | 确认本次不存在该功能/对象/要求；注明依据，不得掩盖材料缺失 |

- 六项汇总每项一行，不增加“部分通过”。不同页面/状态结果在业务明细保留；UI/框架的差异在该项证据中简列覆盖、失败及未验证子项，必要时附验证记录。有确定不满足则汇总不通过；没有失败但有适用范围未验证则未验证；全部适用范围通过才通过；全项无适用对象才不适用。失败与未验证并存须同时披露，不以代表页替代全部页面。
- 证据写实际材料位置、命令及结果、操作/预期/实际、尚保留的截图路径或可追溯旧记录；已清理截图使用包含版本、页面/状态和实际观察的文字验证记录，不留失效链接。C04 通过须真实操作；C05 外观通过须截图复核，名称/尺寸等独立子项可用 DOM/自动证据；C06 动态行为和三个自动检查须实际执行。静态代码可证明缺陷，不能证明运行/视觉通过；只截图失败时保留有效操作/DOM/自动证据，仅视觉子项未验证。
- 无关联 Demo 且非本轮交付对象时，C03～C06 不适用，C01/C02 照常审查。要求交付却缺失或读不到的 Demo 属于适用而未验证；已静态证实的缺陷仍判不通过。无某类表单/筛选/浮层仅对应子项不适用。工具失败不是业务缺陷。
- 独立工具失败的本地兜底在执行说明标“独立性未验证”及原因，不增加第七项；六项可依实际本地证据给结果，不能声称独立审查通过。
- 可选审美建议不等于不满足已确认要求；影响阅读/操作或违背基线的缺陷正常记录。

### 固定报告格式

报告依次输出四部分，避免重复的执行、工具和业务清单：

1. **结论与执行说明**：目标/版本、首轮或复查、实际材料、范围、审查者 ID 或兜底原因。分别给出 Spec、Demo 功能、UI 与视觉结论，不互相替代；简述旧问题关闭情况与本轮复查变化。
2. **六项检查清单**：C01～C06 每项一行，列覆盖范围、方法、结果及证据/明细引用。复查标重测或沿用并给记录、版本核对和未变更依据；无有效证据标未验证。不突出类别覆盖率或工具通过数量；需要状态计数时仅统计六行，四种状态合计为 6，不与业务点数量混算。
3. **业务对应与验收明细**：只输出第 4 节的一份统一明细，覆盖全部确认业务点、字段、状态/场景、操作及结果，分别列 Spec 可开发性、三方对应和真实功能验证结果与证据。说明业务覆盖及缺失/未验证项，不以六项类别齐全代替完整业务。详细规则可准确引用材料，不能只填“已核对”。
4. **问题及待验证范围**：按阻塞→重要→建议列 CHK-xx、证据、后果和关闭条件，引用 C 编号及业务明细；同根问题只列一次。集中列材料/工具受限范围及交付影响。报告后按本节“用户逐项决策”依次确认所有适用的不通过/未验证项，不把多项决定合并成一次笼统确认。无问题直说，不凑建议。

| 编号 | 检查项 | 实际覆盖范围 | 检查方式 | 结果 | 证据／明细／问题 |
|---|---|---|---|---|---|
| Cxx | 对应六项之一 | 实际页面/状态及适用子项 | 文档核对／自动检查／真实操作／截图 | 通过／不通过／未验证／不适用 | 实际证据或明细引用；不通过关联 CHK-xx，同时披露未验证范围 |

表格仅为格式示意，每项填实际状态，不将四种状态并列填一格。历史报告旧 C 编号保留在原记录，复查按检查含义归入新六项并注明来源；CHK 编号、关闭条件和已解决状态不变，不因目录合并启动新一轮全面审查。

Spec 可开发性必须根据全部已确认业务的逐页、逐字段、逐状态/场景与逐操作合同判断，不能因没有发现 P0 缺陷就通过。三方一致性以实际明细判定；有已确认业务缺失/冲突，不能宣称 Demo 完整或三方一致性通过。存在本轮必验但未验证的业务范围时，明确列出并保留受限结论，不输出整体交付通过。

Spec 结论按本轮基线与准入后的必改项判断；后续记录但未纳入本轮的旧有局部问题，必须在结论旁单列影响与处理范围，不称为“全部重要问题已解决”，也不混入本轮必改统计。Spec 结论：有阻塞项为“受影响范围暂不可进入开发”；无阻塞但有重要项为“主流程明确，受影响部分需补齐后开发”；适用范围检查充分且无阻塞/重要项才为“产品层面可进入开发”。关键材料缺失则为“暂无法判断”。Demo 单独标记“一致性验证通过 / 存在偏差 / 仅静态审查 / 未提供”，并说明交互和视觉覆盖范围。不能用 Spec 通过替代 Demo 可交付，也不能用工具失败否定 Spec。

## 7. 收敛与停止条件

完整业务明细与检查基线在首轮建立；本次用户明确将验收升级为全部业务及三方一致性时，应对旧记录未覆盖的范围做一次补审并更新基线，不能直接沿用旧的仅 P0 通过结论。后续只复核问题和变更影响，禁止借完整性反复扩大已经明确的需求范围。

默认节奏是“一轮全面审查 + 一轮修复复查”，不是两轮后强行通过。第三轮仍有必改项时，先说明原因：原问题未解决、修复引入回归、需求变化或首轮重大遗漏；禁止用每轮增加细节要求维持审查。

本轮基线内必改项达到关闭条件、修改影响范围验证通过、没有符合准入规则的新阻塞/必改项时，明确输出“本轮审查通过”，并按第 6 节区分 Spec 可开发性和 Demo 交付结论。可选建议未采纳不影响通过；不得为了显得审查充分而再附一批必须处理的事项。若验证受限，明确哪个部分待验证，不能假装完成。

清单中的已解决项不能仅凭“已修改”的回复关闭，必须有当前证据。沿用旧编号，新发现使用新编号；不要给同一问题换名称重复提出。已通过且需求/文件未变化时，再次 `check` 返回原结论并按第 6 节保留逐项清单，标明沿用证据和适用范围，不重新发掘建议；用户明确要求新的全面审查除外。历史记录或当前版本无法核实时，应说明限制，不直接沿用通过结果。

首次审查报告完成后进入“用户逐项决策”阶段，不得在确认完成前修改目标材料。所有适用不通过/未验证项的处理决定闭环后，继续按“修改与复查”阶段完成用户已确认的修改与验证；若用户选择保留某项，则保留其原状态和限制并继续其余已确认工作。修复验证结束后交付最终 C01～C06 与业务明细状态，明确哪些项关闭、哪些仍不通过/未验证及其用户决定。
